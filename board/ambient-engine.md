## 사용자 성향 — 원하는 것 / 불편해하는 것
- **음악이 좋은지 스스로 판단하기 어려워한다** ("이게 좋은건지 나는 몰라서") → 그림과 함께 보여 주고, 비교할 기준(참고 채널)을 같이 준다.
- **코드로 그린 도형 그림(클립아트 느낌)은 "최악"** → 영상 그림은 사진·실사 수준이 기본.
- 어둡고 무거운 소리는 싫어한다 → 장조·높은 음역 기본.
- **보고가 길면 뭘 하라는 건지 못 알아듣는다** ("뭐 어떻게 확인하라고"). 폰에서 읽는다 → 지시는 번호 3~4줄, 답은 한 단어로 받게.
- 유튜브 채널이 본래 목적(앱 아님). 기대치는 낮게, 정책 거절 대비(시드 공개·영상마다 다르게)를 처음부터.

## 다른 세션에 알리는 노하우
- **Web Audio 는 iOS 에서 반드시 탭 뒤에 AudioContext 생성/`resume()`**. 무음 스위치가 켜져 있으면 소리가 안 나고, 화면이 잠기면 웹 오디오는 멈춘다(배경 재생은 네이티브 단계에서).
- **생성 음악의 시드 재현성**: 난수 하나를 여러 스트림(코드·멜로디·환경음·귀뚜라미 2마리)이 나눠 쓰면 예약 구간 길이에 따라 소비 순서가 바뀌어 같은 시드가 다른 곡이 된다. **스트림마다 RNG 를 따로** 둔다. 검증은 OfflineAudioContext 렌더 비교 — 단, 크롬 렌더는 1e-8 수준 부동소수점 차이가 있으니 허용 오차로 비교.
- 엔진을 "오디오 시계 t1 까지 예약" 구조로 짜면 실시간(setInterval 로 6초씩)과 오프라인 렌더(한 번에 N초)를 같은 코드로 쓴다 → 헤드리스 검증·WAV 추출이 공짜.

- **렌더 속도**: 헤드리스 크롬 OfflineAudioContext 3분 렌더가 비 348초·모닥불 78초·카페 약 2분. 비는 빗방울마다 노드를 새로 만들어서 느리다 → 8시간(160배)은 이대로 불가. ② 전에 빗방울을 미리 만든 버퍼 재생으로 바꾸거나 1시간 조각을 이어 붙인다.
- 오프라인 렌더 꺼내기: AudioBuffer → Int16 → base64 10초 조각씩 `page.evaluate` 로 받아 ffmpeg `join`+`loudnorm`(I=-18).

- 렌더 속도 개선: 빗방울·장작을 미리 만든 소리 조각(BufferSource 1개+Gain)과 고정 팬 버스 5개로 → 비 3분 348초 → 140초. 남은 병목은 피아노(음마다 노드 7개).
- **헤드리스 테스트 크롬(chromium-1194)은 H.264 를 못 튼다** (`canPlayType` 빈 값) → 영상 페이지 재생 확인은 ffmpeg 전체 디코딩 오류 0 + 프레임 추출로. 아이폰 사파리는 H.264/AAC 기본 재생.
- `pkill -f <스크립트이름>` 이 내 bash 명령까지 죽인다(PLAYBOOK 에 이미 있는 교훈, 또 밟음) → `timeout 60 node …` 로 감싼다.
